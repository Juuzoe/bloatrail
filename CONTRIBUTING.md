# Contributing to Bloatrail

Thanks for considering it. The most useful contributions are **new detectors**:
if Bloatrail doesn't recognise something that eats your disk, that's a real gap.

## Getting set up

```bash
git clone https://github.com/Juuzoe/bloatrail
cd bloatrail
cargo build
cargo test
```

Rust 1.82 or newer. No other tooling is required.

## Before you open a pull request

```bash
cargo fmt --all
cargo clippy --all-targets --all-features -- -D warnings
cargo test
```

CI runs `clippy` and `test` on Linux, macOS and Windows; `rustfmt` is
platform-independent so it runs once on Linux. There is also a rustdoc build
with warnings denied and a check against the minimum supported Rust version.

## Adding a detector

Detectors live in [`src/detectors/`](src/detectors), one module per ecosystem.
A detector is a pure function of [`DirContext`](src/analysis/context.rs) — it
performs no I/O, because everything it is allowed to know was already gathered
during the directory walk.

1. Add the marker files your ecosystem uses to `Markers` in
   [`src/analysis/context.rs`](src/analysis/context.rs), and teach
   `Markers::observe` to recognise them.
2. Write the detector.
3. Register it in `detectors::all()`.
4. Write tests.

```rust
pub struct MyToolCache;

static TRIGGERS: &[Trigger] = &[Trigger::Name(".mytool-cache")];

impl Detector for MyToolCache {
    fn id(&self) -> &'static str {
        "mytool.cache"
    }

    fn triggers(&self) -> &'static [Trigger] {
        TRIGGERS
    }

    fn detect(&self, ctx: &DirContext<'_>) -> Option<Detection> {
        if !ctx.parent_is_project(Markers::MYTOOL_CONFIG) {
            return None;
        }
        Some(
            Detection::new(
                Category::Cache,
                Confidence::High,
                CleanupSafety::Safe,
                "MyTool build cache",
            )
            .with_technology(Technology::MyTool)
            .with_evidence("A `mytool.toml` file exists in the parent directory.")
            .with_evidence("Regenerated by the next build.")
            .regenerated_by("mytool build")
            .collapsed()
            .with_specificity(SPEC_CONTEXT),
        )
    }
}
```

### The rules a detector must follow

**Demand context.** A rule that fires on a directory name alone is a bug. If the
name is genuinely unambiguous (`node_modules`, `__pycache__`, `dist-newstyle`),
you may report `Confidence::Medium` without corroboration — but a name shared
with the rest of the world (`build`, `dist`, `out`, `bin`, `target`, `cache`)
must find a marker file before claiming anything.

**Be honest about safety.** The classification is about *recreatability*, not
size:

| Level | Means |
| --- | --- |
| `Safe` | Regenerated automatically by a documented local command. No user data. |
| `ProbablySafe` | Regenerable, but it costs time or bandwidth. Virtualenvs, module caches. |
| `Review` | Might be wanted. A human has to decide. |
| `Dangerous` | Removal is likely to destroy something valuable. |
| `NeverDelete` | Bloatrail will not remove this whatever the flags say. |

Only `Safe` is eligible for unattended cleanup.

**Explain yourself.** Every `with_evidence` line is shown verbatim by
`bloatrail explain`, so write complete sentences that name the evidence you
used. "A `Cargo.toml` file exists in the parent directory" is useful; "matched
rule 7" is not.

**Say what regenerates it.** `regenerated_by` is what turns "you can delete
this" into "you can delete this and here's how to get it back".

**Collapse when appropriate.** `.collapsed()` tells the scanner to measure the
directory exactly but stop retaining and classifying its children. Use it for
opaque trees (`node_modules`, `target`, `.git`). Do not use it for directories
whose contents are worth exploring, like `~/Downloads`; use
`.claiming_contents()` there instead if the whole subtree should count as one
category.

### Tests a detector needs

Two, at minimum:

```rust
#[test]
fn fires_with_project_context() { /* ... */ }

#[test]
fn does_not_fire_without_it() { /* ... */ }
```

The second one is the important one. Use `crate::detectors::tests_support::ctx`
for unit tests — detectors are pure, so no filesystem is needed. Add an
integration test in [`tests/classification.rs`](tests/classification.rs) if the
behaviour depends on real directory structure.

## Changing cleanup safety

Anything that touches [`src/cleanup/`](src/cleanup) needs proportionally more
care and more tests. In particular:

- The dry-run guarantee is structural. `Executor::remove` returns before any
  mutating call when `dry_run` is set, and
  [`tests/cleanup_safety.rs`](tests/cleanup_safety.rs) asserts that every file
  survives. Do not add a mutating call anywhere that bypasses it.
- Every check in `SafetyGuard::verify` exists because something could go wrong
  without it. If you remove one, explain what makes it unnecessary.
- New refusal reasons should read as sentences a user can act on.

## Changing JSON output

The schema in [`src/output/json.rs`](src/output/json.rs) is a contract. Adding
an optional field is fine. Renaming, removing or changing the meaning of a field
requires bumping `SCHEMA_VERSION` and saying so in the pull request.

## Style

- Follow `rustfmt` defaults; CI enforces them.
- Prefer enums to strings and `Option` to sentinel values.
- Comments should explain *why*, not restate *what*. If a line needs a comment
  to say what it does, the line probably wants rewriting instead.
- No `.unwrap()` on anything that can fail at runtime. Tests are exempt.
- Public items need doc comments; `#![deny(missing_docs)]` is on.

## Reporting bugs

A misclassification report is most useful with:

- The output of `bloatrail explain <path>`.
- A listing of the directory and its parent (`ls -la`), since that is exactly
  the evidence the classifier saw.
- What you expected instead, and why.

If Bloatrail proposed removing something it should not have, please say so
prominently — that is the highest-priority class of bug in this project.
